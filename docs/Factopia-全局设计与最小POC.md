# Factopia 全局设计与最小 POC 方案

> 依据：《AI 驱动的跨境量化股票策略研究平台》spec
> 版本：v0.2（2026-10-06）：新增第 7 节「开发与部署环境」
> 状态：草案，待评审

---

## 1. 设计目标

把一个投资假设（人工提出或 AI 自动挖掘）在**香港、英国、法国**三个市场上分别做时间点一致的验证，判断它能否跨市场迁移，再按客户授权构建组合并拆分汇率贡献。全过程留痕、可复现，关键节点由人工审批。

全局设计遵循三条原则：

1. **组件独立**：数据、因子研究、自动挖掘、文本信号、组合、治理各自是独立的 Python 包，通过明确的输入输出（文件、表、CLI，后续加 MCP）对接，不绑定任何编排层。
2. **三个市场分开跑，结果放在一起比**：同一信号定义在三个市场独立运行，不合并样本；比较放在最后一步。
3. **AI 产出只是候选**：自动挖掘的因子、生成的文本信号，都必须先过统一验证关卡和人工评审，才能进入因子库。

## 3. 最小 POC

### 3.1 要证明什么

1. 三个市场的数据（行情、外汇、日历）能统一标准化，并能分别构建 Qlib 数据集；
2. **同一套因子在三个市场独立评估**，并按规则自动分类为"三市场通用 / 地区特定 / 需调参 / 扣成本后无效"；
3. **RD-Agent 能在香港、英国、法国三套数据上分别运行**，挖出的候选因子经过统一验证关卡后再入库；
4. 按一份模拟客户授权构建三市场组合，报告**本地币种收益、基础币种收益和汇率贡献**；
5. 每次运行的代码、参数、数据快照都记入 MLflow，可以复现。

### 3.2 范围

| 项 | 最小 POC 的取值 |
|---|---|
| 市场和股票池 | 香港：恒指成分股；英国：富时 100；法国：CAC 40（全部用当前成分股） |
| 数据 | yfinance 日线（已复权）、汇率（`GBPHKD=X`、`EURHKD=X` 等） |
| 时间范围 | 2015-01 至今；训练集 2015–2021、验证集 2022–2023、测试集 2024 至今（测试集在挖掘过程中完全不使用） |
| 预测目标 | 未来 20 个交易日收益（约 1 个月，对应 spec 演示案例） |
| 基础因子 | Qlib Alpha158 |
| 自动挖掘 | RD-Agent `fin_factor`，三个市场各跑一轮，同一挖掘方向 |
| 组合 | 月度调仓，只做多，相对复合基准（^HSI、^FTSE、^FCHI 按授权权重合成） |
| 基础币种 | 可配置，默认 HKD（模拟客户服务地在香港） |
| 治理 | 只做最简版：YAML 规则包（受限证券、卖空禁令、集中度）+ MLflow 留痕 |
| 交付形式 | Python 项目 + CLI + **Web 界面（每个步骤都有页面展示，可从界面触发运行）**；每次运行输出一份中文 HTML 报告 |

### 3.3 不在最小 POC 范围内（放到后续阶段）

- 多语言文本信号（L1-C）：受公告数据的获取和许可限制，放到阶段 1；
- 跨地区审批流、信号目录、监控仪表板（L4、L5）；
- 协作平台集成（L6）；
- 时间点一致的基本面数据、真实交易成本模型。

### 3.4 数据处理要点

- **英股单位**：yfinance 中 `.L` 股票以便士（GBX）报价，统一除以 100 转为 GBP。
- **交易日历**：每个市场按自己的交易日历评估因子；组合层按三个市场交易日的并集对齐，某个市场休市的日子沿用前一日价格，汇率按日更新。
- **时区**：所有时间戳统一存为 UTC，同时保留本地交易所时间。
- **Qlib 适配**：Qlib 内置区域配置（如 `REG_CN`）带有 A 股规则（涨跌停、100 股一手），需要为三个市场写自定义配置：取消涨跌停，按市场设置交易单位。港股每手股数因股票而异，POC 阶段简化为按金额成交。
- **已知偏差**：使用当前成分股会带来幸存者偏差，报告中要明确标注；生产阶段需要换成历史成分股数据。

### 3.5 统一验证关卡（POC 版本的阈值，可配置）

| 检查 | 规则 |
|---|---|
| 样本外 | 只看验证集表现做筛选；测试集只在最终报告时使用一次 |
| 多重检验 | 记录挖掘过程中试过的全部因子数量；入选门槛为 RankIC 的 t 值 > 3 |
| 去冗余 | 与已入库因子的相关性 > 0.7 时只保留较强的一个 |
| 中性化 | 对规模、动量、波动率中性化后，RankIC 方向不变 |
| 成本 | 扣除各市场成本和税费后，Top 组合超额收益仍为正 |

**迁移性分类**（基于三个市场各自在验证集上的 RankIC）：

| 分类 | 判定 |
|---|---|
| 三市场通用 | 三个市场 RankIC 方向一致，且都通过显著性门槛 |
| 地区特定 | 只有一个或两个市场通过 |
| 需调参 | 方向一致但部分市场未通过门槛，调整参数后通过 |
| 扣成本后无效 | 成本前通过，成本后不通过 |

### 3.6 组合层

- **约束来源**：从模拟授权 YAML 和规则包读取，转换成 skfolio `MeanRisk` 的参数。

  | 授权条款 | skfolio 参数 |
  |---|---|
  | 风险预算 | `max_tracking_error` |
  | 不允许卖空 | `min_weights=0` |
  | 受限证券 | 对应股票 `max_weights=0` |
  | 单一市场上限 | `groups` + `linear_constraints` |
  | 换手上限 | `max_turnover` |
  | 交易成本 | `transaction_costs`（按市场设置） |

- **多币种收益**：基础币种收益 =（1 + 本地收益）×（1 + 汇率收益）− 1；报告中分别列出本地股票收益和汇率贡献。POC 只做不对冲汇率的情况。
- **成本和税费**：按市场在规则包中配置，带版本号和"待合规确认"标记，不写死在代码里。以下为示例值：英国买入印花税 0.5%；香港买卖双方印花税各 0.1%；法国大市值股票买入金融交易税 0.4%。
- **归因**：Brinson 归因（按市场分配效应、选股效应和汇率贡献）。

### 3.9 运行环境

- **全部在 Docker 中运行**，本地（Mac / Windows）和云服务器使用同一套镜像和 compose 配置，详见第 7 节。
- **自动挖掘**：云服务器到位前在本地 Docker 中运行（使用多架构 Qlib 镜像）；到位后迁到云服务器。
- **LLM**：DeepSeek，或公司批准的模型。只向模型发送因子代码和统计结果，不发送原始数据。

### 3.10 里程碑（估算，按一人全职）

每个步骤的后端和对应页面在同一周内完成，做完一步就能在界面上演示一步。

| 周 | 后端 | 界面 | 产出 |
|---|---|---|---|

### 3.11 成功标准

- [ ] 一条命令即可拉取并标准化三个市场的数据，并生成三套 Qlib 数据集；
- [ ] Alpha158 在三个市场的 IC 对比报告，每个因子都有迁移性分类；
- [ ] RD-Agent 在三个市场都至少完成一轮挖掘，所有尝试（包括失败的）都记入 MLflow；
- [ ] 组合报告分别列出本地币种收益、基础币种收益和汇率贡献；

- [ ] 任意一次运行都能根据 MLflow 记录复现出相同结果；
- [ ] 每个步骤都有界面页面，能触发运行、实时查看进度和结果；演示模式能自动走完全部步骤。

## 5. 主要风险

| 风险 | 影响 | 应对 |
|---|---|---|
| 公开数据不是时间点一致的数据，且有幸存者偏差 | 回测结果偏乐观 | POC 中明确标注；生产阶段换授权数据 |
| RD-Agent 挖出只在历史数据里有效的假因子 | 因子在实盘中失效 | 统一验证关卡 + 三市场验证 + 人工评审 |
| RD-Agent 适配多市场的工作量超出预期 | 第 3 周延期 | 第 1 周先做最小运行验证（单市场跑通一轮） |
| 公告数据的许可 | 阶段 1 受阻 | 先确认各来源的使用条款 |
| 团队专有因子库能否接入 | 决定基础因子是接入还是重新实现 | 阶段 0 期间确认 |
| 税费和规则的准确性 | 结论有误 | 全部放进规则包，标注"待合规确认" |

## 6. 协作平台（后期，阶段 2 评估）

**候选**：nuke-ai-collaborator。

**能复用的部分**：多进程 Agent 运行时（支持 DeepSeek 等多种模型）、群组隔离（可以对应研究项目或地区团队）、角色 Bot、工具级人工审批与权限规则、子 Agent 权限衰减（适合约束 RD-Agent 这类自主循环）、声明式阶段工作流（状态可序列化和恢复）、MCP 接入、飞书和微信推送。

**接入方式**：阶段 0 和 1 的组件都是独立的 Python 包，到时包装成 MCP server，由平台 Bot 调用，组件代码不用改动。

**需要补的部分**：

1. **业务级审批流**：多角色、跨地区的顺序审批（研究员 → 本地研究员 → 数据负责人 → 合规 / 模型风险 → 投资组合经理 → 运营），支持退回、限定地区使用、例外处理和获批版本锁定。可以作为声明式工作流中的一种新阶段类型来实现。
2. **安全加固**（进入生产前必须完成）：RBAC；MCP 配置改为只有管理员或只能通过部署配置修改（目前等同于任何登录用户都可以在服务器上执行命令）；按地区控制数据访问；容器沙箱完成 Linux 生产环境验证。
3. **量化界面**：信号目录、分市场监控仪表板、审批工作台。

**定位**：POC 阶段可以用作内部演示的编排层；进入生产前必须完成上面第 2 项的安全加固。

## 7. 开发与部署环境

### 7.1 原则

1. **所有运行都在 Docker 中**：数据构建、因子评估、RD-Agent、组合、后端接口都在容器里运行，不依赖开发者本机的 Python 环境。
2. **本地能跑的，上云不改代码**：本地和云服务器使用同一套镜像、同一份基础 compose 配置；环境差异只体现在差异配置文件和 `.env` 中。
3. **代码在宿主机修改，挂载进容器**：改代码不需要重新构建镜像；只有依赖变化时才重建。
4. **数据和代码分开**：`qlib_data/`、`mlruns/` 等数据放在挂载目录，不打进镜像。

### 7.2 本地与云端分工

团队 5 人，Mac 与 Windows 混用；后续会有云服务器（预计 Linux x86）。

| 环境 | 用途 |
|---|---|
| **本地电脑**（Mac / Windows） | 写代码、调试；用小数据集快速验证；前端开发 |
| **云服务器**（Linux x86） | RD-Agent 挖掘（耗时长、耗资源）；三个市场的完整数据构建；共享的 MLflow 服务；演示环境（后端 + 界面）；**正式结果的产出（基准环境）** |

- **基准环境**：ARM 与 x86 的浮点运算和数学库实现不同，同一份代码在不同电脑上的结果可能在小数点后几位有差异。演示和报告使用的正式结果，以及 Spec TRACK-02 的复现验证，**统一以云服务器上的运行为准**。云服务器到位前，临时指定一台机器作为基准环境。
- 也可以用 VS Code Remote-SSH 直接连接云服务器开发，与本地开发方式混用。

### 7.3 Compose 结构

```
docker-compose.yml        # 基础配置：服务定义、镜像、网络
compose.local.yml         # 本地差异：挂载源码、热更新、内存限制较小
compose.cloud.yml         # 云端差异：内存限制较大、自动重启、不挂载源码、使用镜像仓库中的镜像
.env.example              # 环境变量模板（提交到 Git）；每人复制为 .env（不提交）
```

本地启动：`docker compose -f docker-compose.yml -f compose.local.yml up`
云端部署：`docker compose -f docker-compose.yml -f compose.cloud.yml pull && ... up -d`

**服务划分：**

| 服务 | 内容 | 说明 |
|---|---|---|
| `app` | Factopia 数据层、因子评估、验证、组合、FastAPI 接口 | |
| `rdagent` | RD-Agent 主程序 + 因子代码执行环境 | 挂载宿主机的 `/var/run/docker.sock`，按需启动回测容器（见 7.4） |
| `qlib-runner` | Qlib 回测镜像，由 RD-Agent 按需启动 | 使用我们自己的多架构镜像 |
| `mlflow` | 实验追踪服务和界面 | 云端为团队共享 |
| `web` | 前端 | 本地开发时也可直接在宿主机运行，热更新更快 |

**所有环境差异都放进环境变量**：数据路径、MLflow 地址、内存限制、LLM 配置和 API key 等，代码里不写死任何路径或地址。

### 7.3.1 路径约定（2026-10-06 定）

**配置和代码中只出现容器内路径，不出现任何宿主机路径。**

- 数据、日志、密钥放在 Docker 命名卷 `runtime` 中，所有服务统一挂载到 `/workspace/runtime`；
- RD-Agent 启动的回测容器不交给宿主机的 Docker，而是交给 compose 内的独立 Docker 引擎 `dind`（Docker-in-Docker）。`dind` 与 `rdagent` 以相同路径挂载相同的命名卷，因此 RD-Agent 传出的挂载路径都是容器内路径，Mac、Windows、云服务器的配置完全相同；
- RD-Agent 源码在镜像构建时固定为 v1.0.0，放在 `/opt/rdagent-src`，通过命名卷 `rdagent_src` 与 `dind` 共享；
- 唯一与宿主机文件系统相关的是本地开发时以相对路径 `.` 挂载源码（`compose.local.yml`），与数据路径无关；
- 代价：`dind` 需要 privileged 模式；回测镜像需载入 `dind`（`docker save ... | docker compose exec -T dind docker load`），云端可改为从镜像仓库拉取。

### 7.4 RD-Agent 的容器化要点

RD-Agent 的运行分三部分：主程序（调用 LLM、管理循环）、LLM 生成的因子代码（在当前环境的 conda 环境中执行）、Qlib 回测（RD-Agent 自己启动一个 Docker 容器运行 `qrun`）。容器化时需处理以下问题，均可通过环境变量配置解决，**不需要修改 RD-Agent 源码**：

| 问题 | 原因 | 处理 |
|---|---|---|
| 默认回测镜像只有 x86 版本 | 基于 `pytorch/pytorch:2.2.1-cuda12.1-cudnn8-runtime`，在 Apple 芯片上只能模拟运行，很慢 | 用 `QLIB_DOCKER_DOCKERFILE_FOLDER_PATH` 和 `QLIB_DOCKER_IMAGE` 指向我们自己的多架构镜像（`python:3.12-slim` + CPU 版 PyTorch），Qlib 固定到与官方镜像相同的提交 `2fb9380`；`QLIB_DOCKER_ENABLE_GPU=False` |
| 容器中再启动容器 | `rdagent` 服务运行时要启动回测容器 | 使用 compose 内的 `dind` 服务（`DOCKER_HOST=tcp://dind:2375`），见 7.3.1；早期方案为挂载宿主机 Docker 接口，因需写宿主机路径已弃用 |
| 挂载路径必须一致 | RD-Agent 以路径字符串向回测容器挂载数据目录 | `rdagent` 与 `dind` 以相同的容器路径挂载同一命名卷（7.3.1） |
| 默认资源限制超过本地机器 | 默认 `mem_limit: 48g`、`shm_size: 16g` | 本地设置 `QLIB_DOCKER_MEM_LIMIT=8g`、`QLIB_DOCKER_SHM_SIZE=2g`；云端按服务器配置设置 |
| 首次运行自动下载 A 股数据 | `rdagent/utils/env.py` 检查 `cn_data` 目录，不存在即下载 | 运行官方示例时允许下载；切换到我们的数据后，通过数据目录布局或继承扩展跳过该检查（第 3 天实测确定） |
| 模板目录挂载 | RD-Agent 把自身安装目录下的 `factor_data_template` 挂载给回测容器（`scenarios/qlib/experiment/utils.py` 写死为 `Path(__file__).parent`） | 镜像中以可编辑方式安装源码到 `/opt/rdagent-src`，该目录通过命名卷与 `dind` 共享；不修改源码（2026-10-06 实测） |
| 自动下载 A 股数据失败 | RD-Agent v1.0.0 调用 `python -m qlib.run.get_data`，但其固定的 Qlib 提交 `2fb9380` 中该模块已改为 `qlib.cli.data`，属于上游 bug | 自行执行 `python -m qlib.cli.data qlib_data --target_dir ... --region cn`，数据存在后 RD-Agent 跳过下载；可向 RD-Agent 提交修复（2026-10-06 实测） |
| 回测默认不在 Docker 中运行 | v1.0.0 中 `model_coder/conf.py` 的 `env_type` 默认为 `"conda"`，会在 rdagent 容器内建 conda 环境并从源码编译 Qlib（缺编译器即失败），与文档描述不一致 | 设置 `MODEL_CoSTEER_ENV_TYPE=docker`，回测使用我们的多架构镜像（2026-10-06 实测） |
| 日志签名密钥不共享 | 日志文件用随机密钥签名，密钥默认存于容器内 `~/.rdagent`；每次 `docker compose run` 都是新容器，导致日志界面无法读取 | 设置 `ARTIFACT_SIGNING_KEY_PATH` 指向 `runtime/rdagent/.rdagent/artifact_signing.key`，所有 rdagent 容器共用（2026-10-06 实测） |
| 回测偶发 "Metric 'Rank ICIR' is malformed" | Qlib 的 `MLflowRecorder` 用 `AsyncCaller` 在后台线程写指标（`recorder.py` 第 350 行），同一进程随后读取时可能读到未写完的文件；属 Qlib 上游竞态，结果取决于时机 | 回测镜像中加入 `sitecustomize.py` 启动钩子，在 `start_run` 后等待排队写入并改为同步写入；不修改 Qlib 源码文件（2026-10-06 实测） |
| 多市场切换 | 一次运行只针对一套数据；配置模板写死沪深 300、A 股涨跌停和成本；数据目录写死为 `cn_data` | 已实现（2026-10-06 港股实测通过）：`FACTOPIA_MARKET=hk/uk/fr` 时，启动脚本用 `configs/rdagent/<市场>/` 的模板覆盖原版（股票池、基准、region=us、取消涨跌停、成本示例值），回测容器挂载该市场数据（放在 `cn_data` 位置），并使用独立工作目录；每次启动先恢复原版模板 |
| 挖掘时间段 | 默认 2008–2020 年，且未隔离最终测试数据 | RD-Agent 用数据集截止 2023-12-31（`to_qlib --rdagent`）；训练 2015–2020、验证 2021、测试 2022-01-01 至 2023-12-28，2024 年以后对 AI 完全不可见（Spec MINE-03）。测试期结束日须早于数据最后一天，否则 Qlib 回测在最后一步读取下一交易日时越界 |
| 调试数据误用其他市场的旧文件 | RD-Agent 原版 `generate.py` 取"前 100 只股票在 2018–2019 年的数据"生成调试数据；若有股票在该时段无数据（2019 年后上市的港股），生成失败但不中断，模板目录中残留的上次运行（A 股示例）文件被继续使用，导致 AI 写代码、自检时看到的是 A 股样本 | 用 `configs/rdagent/common/generate.py` 替换（只选该时段有数据的股票）；启动脚本每次先恢复原版脚本并删除残留数据文件，生成失败时会直接报错（2026-10-07 港股实测：调试数据为 71 只港股） |
| 持股数沿用 A 股设置 | 原版模板 topk=50、n_drop=5 为沪深 300 设计；用于恒指（84 只）、CAC 40（40 只）时持股占 50%–100%，选股失效 | `factopia/mining/topk.py` 按股票池比例写入各市场模板：持股 20%（与五分位评估口径一致）、最少 8 只；每日换仓为持股数的 10%、最少 1 只。当前：香港 17/2、英国 20/2、巴黎 8/1。此为检验因子的回测规则，不是客户组合 |
| 基准指数参与因子排序 | RD-Agent 用 `D.instruments()`（即 all）生成因子数据 | 基准指数不放入 `all.txt`，单独列在 `benchmark.txt`；回测按代码读取基准，不受影响 |
| AI 缺少场景信息 | fin_factor 发给 AI 的背景只有通用的因子定义、5 个量价字段说明和代码格式，没有市场、研究目的、研究方向等信息（2026-10-07 核对日志；此前记为"场景描述写有 CSI300"有误，该描述出现在其他场景的提示词中），因此 AI 只能提出教科书式的通用因子 | 后续通过替换场景描述与数据说明提供市场背景、研究方向、已有发现和更多数据（Spec 9.5 第 2、3 项）；正式平台中由研究员在界面输入研究方向与客户授权 |

### 7.5 跨平台规范（Mac / Windows）

| # | 规范 | 原因 |
|---|---|---|
| 1 | 镜像使用多架构基础镜像，依赖版本全部锁定 | Mac 为 ARM，Windows 和云服务器为 x86 |
| 2 | **Windows 同事在 WSL2（Ubuntu）中开发**，代码放在 WSL2 文件系统内，不放在 `C:\` 下 | 避免 Windows 路径导致 RD-Agent 挂载失效；文件读写和前端热更新也更快 |
| 3 | 仓库加 `.gitattributes`，强制文本文件使用 LF 换行 | 带 CRLF 的脚本在 Linux 容器中会报错 |
| 4 | 提供 `.env.example`，个人配置放在本地 `.env` | 每台机器内存不同；API key 不能提交到 Git |
| 5 | 宿主机上不写 bash 脚本；命令统一通过 `docker compose run` 或 Python 任务脚本执行 | 三种系统通用 |
| 6 | 文件名统一小写 | Mac / Windows 不区分大小写，Linux 区分 |
| 7 | 编写 `docs/dev-setup.md`，Mac 和 Windows（WSL2）各一节 | 新成员照着做即可跑起来；第 1 周由一位 Windows 同事按文档验证一遍 |

以下事项暂不做，出现需要时再补：CI 自动测试（需要时用 GitHub Actions 的 Linux 环境）、VS Code Dev Containers 配置（个人可选）、容器用户 UID 映射（WSL2 上遇到文件权限问题时再加）。

### 7.6 上云注意事项

| 事项 | 要求 |
|---|---|
| **服务器配置**（POC 粗略估计） | Linux x86，8–16 核 CPU，32–64 GB 内存，200 GB 以上 SSD；不需要 GPU（RD-Agent 量化回测默认使用 LightGBM） |
| **镜像分发** | 镜像推送到镜像仓库（如 GHCR），服务器拉取部署 |
| **访问安全** | MLflow 默认没有登录认证；界面、接口和 MLflow 都不直接暴露到公网，通过 VPN、SSH 隧道或加登录保护访问 |
| **密钥** | API key 只放在服务器的 `.env` 中，不提交到 Git |
| **多人共用资源** | POC 阶段口头协调 RD-Agent 等重任务的运行时间；后续可加简单任务队列 |
| **地区与跨境** | 服务器所在地区，以及向第三方 LLM（如 DeepSeek）发送代码和统计结果是否合规，需提前请合规确认（业务 spec 将隐私与跨境传输列为地区规则的一部分） |
| **迁移** | 按 7.1 的原则开发，从本地迁移到云服务器预计半天到一天 |

### 7.7 Docker 工具许可

Docker Desktop 对员工超过 250 人或年收入超过 1000 万美元的组织要求付费订阅，**按所属公司的规模判断，不按团队人数**（条款以 Docker 官方最新版本为准）。如需授权而尚未取得，可使用兼容 `docker compose` 的免费替代：Mac 用 Colima 或 Rancher Desktop，Windows 在 WSL2 中直接安装 Docker Engine 或使用 Rancher Desktop。云服务器上直接安装 Docker Engine，不涉及 Docker Desktop。
